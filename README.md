1. Для кожного порту з помилкою `Couldn't connect to server` визначте за дампом, хто відхилив з'єднання і яким способом. Якщо такий порт у вашому варіанті один, опишіть, як у дампі виглядав би другий спосіб відхилення.<br>
Помилку Couldn't connect to server дав лише порт 20016, де з'єднання відхилив сам вузол 10.53.0.80 повідомленням ICMP 10.53.0.80 tcp port 20016 unreachable у відповідь на перший пакет SYN. Другий можливий спосіб відхилення виглядав би в дампі як зворотний TCP-сегмент з прапорцями Flags [R.] від сервера з нульовим seq та підтвердженням ack, збільшеним на одиницю відносно seq клієнтського SYN.

2. Два порти дають помилку `curl` з кодом 28. Чим вони відрізняються за значенням `connect` і за дампом? Що це означає для пошуку причини?<br>
На порту 20011 значення connect дорівнює 0.000000, а в дампі видно лише повторні сегменти SYN без жодної відповіді, тоді як на порту 20018 значення connect становить 50.879 мс, оскільки тристороннє рукостискання успішно завершилося і запит передався, але відповіді не надійшло. Для діагностики це означає, що у випадку 20011 проблема знаходиться на рівні мережі або міжмережевого екрана, який відкидає пакети ще до встановлення сесії.

3. Для порту, на якому сервер не відповідає: чи отримав вузол `srv` тіло `order=42`? Наведіть рядок дампу. Чи можна з цього зробити висновок, що замовлення оброблено?<br>
Так, вузол `srv` отримав тіло `order=42: 00:00:00.000023 IP 10.53.0.80.20018 > 10.53.1.1.50428: Flags [.], ack 3587960216, win 508, length 0. Зробити висновок про обробку замовлення не можна, оскільки цей ACK надіслало лише ядро операційної системи при поміщенні даних у приймальний буфер сокета, а сам застосунок міг їх ще не прочитати і не виконати.

4. Для порту, на якому з'єднання скасовано: на якому етапі надійшов сегмент RST? Що клієнт може сказати про виконання запиту?<br>

5. Скільки сегментів SYN надіслано на порт, пакети на який відкидаються, і з якими інтервалами? Чому інтервали саме такі в цій версії ядра?<br>
